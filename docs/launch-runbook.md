# Launch runbook

Exact sequence to take Meomul live on a Google Compute Engine VM. Follow it in order —
several steps fail confusingly if an earlier one is skipped (DNS before TLS, Atlas
allowlist before the API can serve anything).

Nothing here deploys until [Step 8](#8-deploy).

---

## 0. Before you start

| Prerequisite | Check |
|---|---|
| GCP project with billing enabled | `gcloud projects describe <PROJECT_ID>` |
| DNS control for `meomul.com` | You can add A records |
| Atlas access | Can edit Database Access and Network Access |
| SOLAPI sender registered | `01059570418` — confirmed approved |
| Repo pushed | `github.com/jcbkm4/Meomul-AI`, CI green |

---

## 1. Rotate the exposed secrets

The Atlas password and SOLAPI secret were both exposed in a chat transcript. Treat them
as disclosed and replace them before the VM ever uses them.

```bash
./scripts/rotate-secrets.sh          # prints a new JWT_SECRET and COOKIE_SECRET
```

Then, by hand:

1. **Atlas** → Database Access → edit `4komil` → Edit Password → Autogenerate → copy.
   URL-encode any special characters before putting it in the connection string.
2. **SOLAPI** → API Key 관리 → SECRET 재생성 → copy. The secret is only shown once.

Paste all four into `.env.production` (see step 5).

> The current Atlas password is derived from the account name and is guessable
> independently of the disclosure. Use the autogenerated one.

---

## 2. Create the VM

```bash
PROJECT_ID=<your-project> ./scripts/gcp/create-vm.sh
```

Creates a static IP, a firewall rule allowing only 80/443, and an `e2-medium` running
Ubuntu 24.04 in `asia-northeast3` (Seoul). Idempotent. It prints the static IP — you need
it for the next two steps.

---

## 3. Point DNS at it

```
meomul.com        A    <static ip>
api.meomul.com    A    <static ip>
```

**Do this before deploying.** Caddy requests certificates on first start, and Let's
Encrypt validates by resolving the domain. If DNS is not live, issuance fails and Caddy
backs off — you get an unreachable site that looks like a broken deploy.

Confirm before continuing:

```bash
dig +short meomul.com api.meomul.com
```

---

## 4. Allowlist the VM in Atlas

Atlas → Network Access → Add IP Address → the static IP.

Skipping this produces the most misleading failure in the whole process: the API starts
cleanly, reports healthy for a moment, then times out on every query with a server
selection error that looks like a code fault.

While you are there, check whether `0.0.0.0/0` is present. If it is, your cluster — which
also hosts six unrelated projects — is reachable from anywhere on the internet.

---

## 5. Prepare configuration

A filled `.env.production` is already in the repository root, gitignored, with everything
except the two rotated secrets. Fill those in, then get it onto the VM.

```bash
gcloud compute ssh meomul-prod --zone asia-northeast3-a \
  --command "sudo mkdir -p /srv/meomul && sudo chown -R \$USER /srv/meomul"

gcloud compute scp .env.production meomul-prod:/srv/meomul/.env.production \
  --zone asia-northeast3-a
```

Verify no placeholders survived:

```bash
gcloud compute ssh meomul-prod --zone asia-northeast3-a \
  --command "grep -c REPLACE /srv/meomul/.env.production"     # must print 0
```

---

## 6. Bootstrap the VM

```bash
gcloud compute ssh meomul-prod --zone asia-northeast3-a
sudo git clone https://github.com/jcbkm4/Meomul-AI.git /srv/meomul-repo
sudo cp -r /srv/meomul-repo/. /srv/meomul/
sudo bash /srv/meomul/scripts/gcp/bootstrap-vm.sh
```

Installs Docker, creates the uploads directory owned by uid 1000, adds 2 GB of swap so
`next build` is not OOM-killed on a 4 GB machine, and schedules a weekly image prune.

---

## 7. Copy the uploaded media

```bash
./scripts/gcp/sync-uploads.sh      # from your workstation, at the repo root
```

64 MB across 35 files. **This is required, not optional:** 26 member records reference
`uploads/...` paths that exist only on your machine. The rows survive a deploy; the files
do not. Skipping it means broken avatars that look like data corruption.

The media is deliberately not in git — the repository is public, and member avatars and
chat attachments are other people's personal data.

---

## 8. Deploy

```bash
gcloud compute ssh meomul-prod --zone asia-northeast3-a
sudo bash /srv/meomul/scripts/gcp/deploy-vm.sh
```

The script refuses to start if any required variable is missing, builds and starts the
stack, then polls until every container reports healthy — a broken rollout fails the
command and prints the failing service's logs rather than appearing to succeed.

First run takes several minutes: it builds both images and Caddy negotiates certificates.

---

## 9. Verify

Work through all of these before telling anyone the site is live.

```bash
cd /srv/meomul
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"

$COMPOSE ps                                     # every service "healthy", not just "running"
$COMPOSE logs batch | grep -i "index sync"      # indexes reconciled at boot
docker exec $($COMPOSE ps -q api) whoami        # node, not root
```

```bash
curl -sS https://api.meomul.com/health          # {"status":"ok","db":"connected",...}
curl -sI https://meomul.com | head -1           # 200, valid TLS
curl -sI https://meomul.com/uploads/default-avatar.png | head -1   # 200 — media copied
curl -s https://meomul.com/robots.txt | tail -1 # Sitemap points at meomul.com
curl -s https://meomul.com/ko | grep -o '<html lang="ko"'          # per-locale SSR lang
```

In a browser:

- [ ] Sign up, sign out, sign back in — session survives a refresh
- [ ] **Password reset end to end** — the SMS actually arrives at a real handset. This is
      the one path that cannot be verified from the command line, and the first time the
      SOLAPI credentials are genuinely exercised.
- [ ] Open a chat — the websocket connects and stays connected
- [ ] Upload an image
- [ ] Make a booking

---

## 10. After launch

- **Atlas backups** — confirm they are enabled and take a restore drill. Nothing else in
  this stack protects the data.
- **Uptime monitor** on `https://api.meomul.com/health`.
- **Sentry** — set `SENTRY_DSN_API`, `SENTRY_DSN_WEB` and `NEXT_PUBLIC_SENTRY_DSN`, then
  redeploy. Without them the SDKs stay inert and errors reach stdout only. Note the
  browser DSN is inlined at build time, so it needs a rebuild rather than a restart.
- **Restrict the SOLAPI key by IP** to the static IP. It is currently usable from anywhere.

---

## Redeploying

```bash
cd /srv/meomul
sudo git -C /srv/meomul-repo pull && sudo cp -r /srv/meomul-repo/. /srv/meomul/
sudo sed -i "s/^NEXT_PUBLIC_BUILD_ID=.*/NEXT_PUBLIC_BUILD_ID=deploy-$(date +%Y%m%d%H%M)/" .env.production
sudo bash scripts/gcp/deploy-vm.sh
```

Always bump `NEXT_PUBLIC_BUILD_ID`. It is inlined into the bundle and used as the cache
key for the persisted Apollo cache — leaving it unchanged serves returning users stale
data from before the deploy.

---

## If something goes wrong

| Symptom | Cause |
|---|---|
| Caddy loops, no certificate | DNS not resolving yet (step 3). Check `dig`, wait for propagation. |
| API healthy then every query times out | VM IP not allowlisted in Atlas (step 4). |
| API exits immediately at boot | A required variable is missing, or `SMS_PROVIDER=log` in production — deliberate, it would print reset codes to stdout. |
| Broken avatars, images 404 | Step 7 skipped. |
| `next build` killed, exit 137 | Out of memory — swap missing, so step 6 did not complete. |
| Users logged out after deploy | Expected if `JWT_SECRET` changed. Refresh tokens live in the database and recover on next silent refresh. |

Rollback is manual: check out the previous commit and redeploy. Images are built on the
VM rather than pulled from a registry, so this is a rebuild, not an image swap.
